Campfire installation and upgrades
=================================

Delivery modes
--------------
Campfire includes its compiled React UI. Production hosts do not need Node.js,
pnpm or Vite. Spark remains a separate Linux binary for game hosts.

Use the Docker image or campfire.service for the panel. All game hosting uses
the separate Spark binary, on the panel host or another machine. Same-host
Sparks enroll and connect using the same HTTPS agent protocol as other Sparks.
There is no embedded runtime or local-mode environment setting. Campfire always
runs without Docker access; Spark needs Docker and runs with execution privileges.

Database and persistent panel state
-----------------------------------
SQLite is the default. CAMPFIRE_DATABASE (or --database) accepts a filesystem
path, defaulting to data/panel.db for direct binary runs. The Docker image and
systemd unit default to /var/lib/campfire/panel.db.

To use PostgreSQL instead, create a dedicated database and account and set:

  CAMPFIRE_DATABASE=postgresql://campfire:password@db:5432/campfire?sslmode=require
  CAMPFIRE_DATA=/var/lib/campfire

postgres:// URLs are accepted too. Percent-encode special characters in URL
credentials. Configure TLS through PostgreSQL URL options; use verify-full with
the appropriate root certificate for hostname verification. sslmode=disable is
appropriate only for a trusted local test database. Campfire creates its tables,
indexes and migrations automatically; the account must own its schema and have
permission to create and alter those objects. No PostgreSQL extensions are needed.
PostgreSQL 17 is covered by integration tests in CI.

The release database baseline is version 1. New databases receive the complete
schema in one step. Existing pre-release schemas 5 and 6 are imported without
losing their data, and their migration history is consolidated to one version-1
record. Older pre-release databases must first run commit 204d134. Future release
schema changes will use new migration numbers.

CAMPFIRE_DATA (or --data-dir) stores spark-authority.json and the default SFTP
host key. It defaults beside the SQLite file, or to ./data when using PostgreSQL.
Docker and systemd set it to /var/lib/campfire. Keep this directory persistent
even with a remote database. CAMPFIRE_SFTP_HOST_KEY still overrides the key path.
The supplied Compose file accepts CAMPFIRE_DATABASE from its environment; point
it at your existing PostgreSQL service. The Campfire image needs no extra build.

Both backends use the same application schema and API. Changing the setting
connects to the selected database; it does not copy existing data between backends.
Run one active Campfire process per installation. PostgreSQL support does not
change the in-process scheduler, agent connections or singleton worker model.
Password recovery uses the same CAMPFIRE_DATABASE setting or --database URL.

Notifications and monitoring alerts
-----------------------------------
The Notifications page stores messages with independent read/unread state for
each recipient. The sidebar refreshes its unread badge every 15 seconds. Reading
or marking all read affects only your account. An inbox receives server alerts
only for administrators, the owner and members with server.view at emission;
list, unread counts and read changes recheck current access. Revoked users lose
access to those messages. Spark alerts are administrator-only. New memberships
do not grant old recipients' messages, and disabling external delivery does not
disable the inbox. Notifications are distinct from audit and operation history;
their messages and read receipts persist independently of those retention limits.

Monitoring runs on Campfire, even without any browser connected. Defaults:

  CAMPFIRE_ALERT_CPU_PERCENT=90
  CAMPFIRE_ALERT_MEMORY_PERCENT=90
  CAMPFIRE_ALERT_DISK_PERCENT=90
  CAMPFIRE_ALERT_DURATION_SECONDS=120
  CAMPFIRE_ALERT_INTERVAL_SECONDS=30
  CAMPFIRE_ALERT_HEALTH_ENABLED=true

Percentages are relative to each server's allocation: 180% CPU usage on a
two-core allocation is 90%. A percentage of 0 disables that resource alert;
otherwise choose 0–100. The interval is 5–3600 seconds and the sustained duration
0–86400 seconds. Health conditions include enabled Sparks disconnecting,
unavailable server monitoring, failed/dead runtime states and quota verification
failures while a game is running. Intentionally stopped, deleted or uninstalled
games do not trigger downtime alerts. This does not probe game ports or infer
an unexpected stop from an otherwise healthy stopped container.

Both alert and recovery conditions must persist for the configured duration.
Resource recovery uses a five-percentage-point dead band. Missing/stale samples
do not become healthy samples, and gaps reset pending timers. Disabled Sparks
are excluded. Each state transition creates one message; active state is saved
so polls and restarts do not repeat an active alert. Optional Spark metrics
capabilities and existing Docker/filesystem checks continue to apply.

Optional Apprise delivery follows DockDash's JSON notification contract:

  CAMPFIRE_APPRISE_URL=http://apprise:8000/notify/campfire
  CAMPFIRE_APPRISE_TAGS=admins,homelab
  CAMPFIRE_APPRISE_URLS=discord://webhook_id/webhook_token

Set the complete notify endpoint. Tags and inline target URLs are optional
comma-separated lists, sent as tag and urls arrays along with title, body and
type. Existing Apprise configurations can route the message without inline URLs.
The endpoint is operator-controlled and may be on a private network. Protect
credential-bearing settings as deployment secrets; they are never returned to
the browser or included in delivery errors. Requests time out after five seconds
and redirects are rejected. No Apprise binary or embedded service is required.

Apprise is a global operator destination and receives monitoring messages for
all servers; it is not a per-user routing configuration. The inbox is committed
before external delivery. A background outbox attempts queued messages, with up
to five attempts and exponential delays starting at 30 seconds. External failures
leave messages and read state intact. Admins can inspect queued/failed counts,
send a test and retry exhausted deliveries from Notifications. Test messages are
stored only in the requesting admin's inbox and also queued when configured.
Delivery can duplicate if the remote service accepted a request before a lost
acknowledgment or panel crash. No game-server action is retried by this worker.

Disabling Apprise pauses its existing queue. Enabling it resumes that queue;
messages created while disabled are not backfilled. Set environment values in
the systemd environment file or Compose .env and restart/recreate Campfire.
Notification API tokens can use notifications.read, notifications.write and the
admin-only notifications.manage scopes. Server messages additionally require
server.view; Spark messages additionally require sparks.manage. Scopes never
grant permissions beyond the underlying user and their recipient assignments.

Files, archives and SFTP
------------------------
The Files drawer supports uploads up to 1 GiB per file by default. Set
CAMPFIRE_MAX_UPLOAD_MIB (or --max-upload-mib) on Campfire to change this maximum
for browser and SFTP uploads. Values are integer MiB from 1 through 102400;
for example 512 allows 512 MiB. Restart/recreate Campfire to apply the setting.
The Files drawer displays the configured limit; the panel and Spark enforce it
for declared-size uploads and unknown-size SFTP writes. Disk allocations still
apply. Browser-streamed downloads support up to 100 GiB per file independently
of the upload setting. Transfers use at most 1 MiB per
Spark message. The text editor retains its 1 MiB limit. Uploads show progress
and cancellation, create new files, and publish only after all byte ranges have
arrived. Failed or cancelled uploads leave the destination unchanged. A lost
final response can mean the upload succeeded; refresh before resubmitting.

Downloads check the file's size and modification timestamp between chunks and
stop if it changes. Stop the game for a consistent snapshot of actively written
files. HTTP downloads and SFTP handles recheck current token/account validity
and server permissions on each chunk. Browser downloads use the normal session;
API clients can use bearer authentication on:

  GET /api/v1/servers/{id}/files/download?path=world.dat

Compression creates .tar.gz archives. Extraction accepts .zip, .tar.gz and .tgz
and requires a new destination folder; it does not merge into or overwrite an
existing directory. Select Compress or Extract beside an entry in Files. Archive
operations require a stopped game and are limited to 30 minutes, 100 GiB of
expanded content and 100,000 entries. ZIP directory metadata is capped at 128 MiB
and validated before parsing; multipart and self-extracting ZIPs are unsupported.
Paths, duplicate entries, symlinks, hard
links and special files are rejected. Extracted files/directories receive the
Ember's game ownership. Operations stage results inside the quota-controlled
game filesystem and remove staging on failure. Leave room for both input and
output. Interrupted uploads expire after an hour and staging is cleaned on the
next file request; uploads do not resume after a Spark restart.

SFTP is an optional gateway on Campfire, disabled by default:

  CAMPFIRE_SFTP_LISTEN=0.0.0.0:2022
  CAMPFIRE_SFTP_HOST_KEY=/var/lib/campfire/sftp_host_key

The key path defaults to sftp_host_key in the panel state directory. Campfire
creates an Ed25519 host identity once; preserve it with panel state and verify its SSH
fingerprint in your client. With Docker, also publish the configured TCP port
(for example add "2022:2022" under Compose ports). Ordinary HTTP reverse proxies
do not forward SFTP. No additional listener or inbound port is needed on Sparks.

Connect your SFTP client to Campfire's SFTP address. Use the server ID shown in
the Files drawer as the SSH username and a personal API token as the password.
The token requires server.view and server.operate (or all permissions), and the
user must currently have those permissions for that server. OIDC users use the
same token flow; disabling local browser login does not disable API tokens.
SFTP exposes only that server's game files: no shell, exec, forwarding, symlinks,
ownership changes or chmod. Listing, download, mkdir, rename, empty-directory
removal and atomic uploads are supported. Existing files can be replaced by
an explicit truncating upload; append, resume and in-place editing are not
supported. Replacement checks that the destination did not change during upload.
Mutations require a stopped server and are audited with user and token IDs.
Connections last at most 45 minutes, with at most 64 connections globally and
eight open uploads per server. Campfire and Spark must both advertise the file
transfer/archive capabilities; older Sparks return an explicit capability error.

Personal API tokens
-------------------
Open API tokens from your account in the sidebar to create a named credential.
Choose an expiry of 1 to 365 days and either all your permissions or a restricted
set of scopes. Each user can have up to 50 active tokens. Copy the secret when
created: Campfire shows it once and stores only its SHA-256 hash.

Send the token in the Authorization header, for example:

  curl -H "Authorization: Bearer $CAMPFIRE_API_TOKEN" \
    https://campfire.example.com/api/v1/servers

Bearer requests do not require a CSRF token. Browser session requests still do.
Tokens cannot access browser authentication or token management endpoints; use
your browser session to create, list and revoke your own tokens. Secrets are
never accepted in URLs. An invalid Authorization header fails authentication
even if a valid session cookie is also present.

A token inherits its user's current role, ownership and server memberships;
scopes only restrict that access. Spark administration remains admin-only.
Server operation scopes also require server.view. Revoke a token from the same
dialog to block further requests. Expiry, disabling/deleting the account and
password or account role changes invalidate existing tokens. Membership and
role permission changes take effect on subsequent authorization checks.
Console streams and backup downloads recheck access while running. Revocation
does not cancel operations or recurring schedules already accepted by Campfire.
Audit records identify token-authenticated changes by user and token ID.

API tokens work for local and OIDC accounts, including when local password
login is disabled. Disabling local login only disables browser password login.
Keep browser/identity-provider access available for token management.

Backups, off-host storage and retention
--------------------------------------
Backups require the negotiated server.backups.v1 capability. Local deletion
additionally requires server.backups.delete.v1; S3 restoration requires
server.backups.remote.v1. See Spark feature negotiation below.
Archives are first completed on the Spark, whether created manually or by a
recurring backup schedule. A Campfire background worker discovers them, uploads
eligible copies, and retries failures after restarts. Server operation history
records creation/restoration; the Backups dialog shows local/S3 availability,
synchronization errors and pending deletion. Uploads do not stage files on panel
disk. They use SHA-256 validation and checksummed S3 multipart uploads, keeping
the local archive when synchronization fails.

Configure S3 only on Campfire (see config/campfire.env.example):

  CAMPFIRE_S3_BUCKET=campfire-backups
  CAMPFIRE_S3_REGION=us-east-1
  CAMPFIRE_S3_PREFIX=campfire

The AWS SDK credential chain supports AWS_ACCESS_KEY_ID, AWS_SECRET_ACCESS_KEY,
an optional AWS_SESSION_TOKEN, shared AWS configuration, and instance roles.
Credentials are not stored in server configuration or sent to Sparks. For
S3-compatible services, set CAMPFIRE_S3_ENDPOINT and, when required,
CAMPFIRE_S3_PATH_STYLE=true. Both Campfire and Sparks must be able to reach and
trust the storage endpoint; Sparks download off-host restores directly using a
short-lived URL for one object. Redirects are rejected. No new public Spark port
is required, and URLs are not retained in status, audit or operation history.

Grant the service account bucket ListBucket access restricted to the configured
prefix, and object GetObject, PutObject, DeleteObject and AbortMultipartUpload.
Versioned buckets additionally need GetObjectVersion and DeleteObjectVersion.
Campfire records object version IDs and removes the owned version on deletion.
Configure bucket lifecycle cleanup for incomplete multipart uploads left by a
host crash. Do not apply an external lifecycle policy that expires managed
objects sooner than Campfire's retention policy.

Enable background S3 sync per server in Backups > Storage and retention.
Configure local and S3 retention independently by newest-copy count and maximum
age in days. Zero disables that limit; automatic deletion is off by default.
For example, set Local copies to keep = 3 and S3 copies to keep = 1. Sync uploads
the eligible newest archive, retains older local copies up to the local limit,
and prunes older S3 copies only after the newer upload succeeds. A local archive
awaiting a required upload is protected. Retention settings apply to both
manual and scheduled backups. Existing local storage still has its 1000-archive
ceiling; configure local retention when using long-running backup schedules.

Backups can be downloaded through Campfire even while their Spark is offline
when an S3 copy is available. Restoring requires a connected, stopped server.
Spark verifies downloaded size and SHA-256 before publishing the archive, then
uses the existing contained restore validation; failure preserves game data.
The restore cache is subject to local retention. Back up Campfire's database as
well: its catalog records object keys, versions, checksums and server ownership.
Keep the configured bucket, endpoint and prefix stable while managed backups
exist. Campfire rejects mismatched storage settings instead of accessing another
bucket. Retention changes cannot recover deleted copies or cancel deletion
already in progress.

Users with server configure permission can change policies and delete local or
S3 copies separately. Operators retain creation, download and restore access.
Deleting one copy keeps the other; explicitly deleting an S3 copy suppresses
background reupload of that archive. Deletion intent is durable and retries when
storage is available. Cleanup waits for active server operations and transfers.
Deleting a server also removes its managed S3 versions before deleting local
game data, backups and database reservations; unavailable S3 blocks completion.

Editing running servers
-----------------------
Server settings can be saved while a server is running or unavailable. Saving does not restart
it; game configuration changes apply on the next restart. Resource increases
reserve capacity immediately. Stop the server before reducing CPU, memory or
disk reservations, or removing/replacing reserved host ports, so resources still
in use cannot be assigned to another server. When unavailable, existing resource
and port reservations remain protected until a stopped state can be confirmed.
Names and descriptions can be edited in every state, including during active
operations and transfers. Those operations restrict game settings, resources and
ports. Ember revision changes continue to require a stopped server.

Server Ember revisions, updates and reinstalls
---------------------------------------------
Each Ember has one local definition. Editing it or accepting a remote update
replaces that definition while retaining its ID. No version history is stored.
Servers retain an applied revision hash and show Update Ember when it differs
from the current local definition. A platform administrator with
servers.manage_all can stop a server and review Update Ember from Servers.

The revision editor keeps shared editable variable values and existing port
mappings. New or locked variables use the selected definition's defaults;
removed variables are dropped. Review images, startup, runtime UID, working
directory, variables and required ports. Invalid values, missing port mappings
and reservation conflicts reject the whole change. A stale Ember pin requires
reopening the editor. Ownership, members, schedules and server identity stay
attached, and other servers keep their existing applied revision hashes.
While an update is pending, existing Spark configurations continue to support
lifecycle operations. Apply the update before changing game configuration,
synchronizing configuration, installing game files or transferring the server.

Applying a revision changes saved configuration only. It does not run the
installer, change game files, or start the server. The next configuration
delivery uses that revision. Select Reinstall when an installer run is required,
then choose Reinstall keeping files or Clean install. This requires server
configure and operate permissions, a stopped server, and no active transfer.
Both modes pull current runtime and installer images before rerunning the pinned
Ember installer, reapply configuration and ownership, and leave games stopped.

Keeping files retains the game directory, but the Ember installer may overwrite
files. Clean install permanently clears the game directory, including worlds,
mods and game configuration. Both modes preserve backups and saved server settings.
Take a backup before changing
revisions or running installers. There is no automatic game-data rollback.
Progress and results appear in server status and retained execution history.
A failed or interrupted installer keeps its files and prevents starting an
incomplete installation. Review Console output, then explicitly retry Install,
or Reinstall. Operations are never silently replayed after a Spark restart.

Spark feature negotiation
-------------------------
On each authenticated connection Spark advertises its supported wire-version
range and versioned capabilities. Campfire selects the highest wire version in
the shared range and the intersection of supported features. Every later
message uses that selected version. Builds currently support wire format 1;
pre-release wire-format-7 Sparks must be updated alongside Campfire before they
can reconnect. A future build can advertise a newer maximum while retaining
format 1 support.
Disjoint ranges are rejected. The Spark release version is informational and
does not determine compatibility.

Optional features evolve through capability names instead of forcing a wire
version change. New incompatible behavior for a feature needs a new capability
version; adding a compatible feature does not. Unknown advertised names are
ignored. Missing advertisements grant no features, and negotiated support is
replaced on every reconnect. Update pre-negotiation Sparks to enable operations.

In Sparks, expand Features to inspect the connected agent version, selected
wire protocol and available features. Offline or disabled Sparks have no live
capability information. This state belongs to the current authenticated session
and is not saved as a claim about future connections.

Capability                         Behavior
server.configure.v1                Saved configuration delivery
server.ember.behavior.v1           Extended config parsers, readiness and stop templates
server.lifecycle.v1                Status, logs, console input and power actions
server.files.v1                    Contained game-file management
server.backups.v1                  Local backup creation, reading and restoration
server.backups.delete.v1           Local backup deletion
server.backups.remote.v1           Restoration from a signed off-host backup URL
server.metrics.v1                  Measured CPU, memory and disk reporting
server.console.stream.v1           Continuous console streaming
server.disk-quota.v1               Continuous game-filesystem quota enforcement
server.transfer.v1                 Fenced server archive transfer steps
server.upgrade.v1                  Explicit update and reinstall workflows
server.reinstall.clean.v1          Clean reinstall while preserving backups
spark.self-update.v1               Verified client binary replacement and restart

Operations can require several features: install/start/restart require quota
support; updates/reinstalls additionally require upgrade support; clean reinstall
also requires server.reinstall.clean.v1; remote restores
require lifecycle, local backup, quota and remote backup support. Transfers check
both Sparks before creating a reservation. Every actual dispatch and Spark-side
execution checks negotiated support again. Unsupported operations return a clear
capability error (HTTP 409) while supported operations remain available on the
same connection. No unsupported operation is automatically substituted or retried.

Capabilities identify implemented behavior, not current Docker/filesystem health.
Quota preparation and verification still have to succeed on the host before a
game runs. Certificate enrollment and renewal use their existing HTTPS endpoints
independently of WebSocket feature negotiation.

Spark client updates
--------------------
Campfire checks the official GitHub repository for the latest stable Spark
release at startup and once per hour. Page refreshes use the cached result.
The repository and release endpoints are constants in shared/sparkrelease;
SparkReleaseCheckInterval in service/spark_update.go controls the hourly interval.
Failed checks retain the last known release and report an error in update status.

Connected clients with a lower semantic version show Update Spark in the Sparks
list and details drawer. Administrators confirm each update. Clients need the
spark.self-update.v1 capability; older clients require one manual upgrade first.
Development version labels are not treated as outdated stable releases.

Spark downloads the official architecture package, checks SHA-256, and extracts
only the regular Spark executable. The staged binary must report the requested
version and support the negotiated panel wire protocol. It refuses replacement
while operations, uploads or server transfer fences are active. The old binary
is retained as spark.previous, replacement is atomic, and a clean re-exec keeps
the existing identity, state directory and game containers. If exec fails, the
old executable is restored. The panel waits for a reconnection reporting the new
version before marking the UI update complete. Binary directories must be writable;
immutable container images are updated by replacing the image instead.

Spark certificates and transfers
-------------------------------
Spark renews its enrolled client certificate automatically when fewer than 30
days remain, checking every 15 minutes while connected. Renewal keeps the same
identity and private key, saves credentials before reconnecting, and does not
restart games. The previous certificate remains accepted for up to seven days,
bounded by its original expiry, so interrupted renewal responses can be retried.
Campfire also renews its private CA certificate with the same signing key when
less than a year remains. Keep the CA key and Spark identity files backed up.
The public HTTPS server certificate is managed separately by the operator.

An offline Spark whose certificate expires needs a new enrollment token for that
same Spark. Enroll using its existing data directory to retain games and its
saved identity. Remove the token from configuration after enrollment succeeds.

Admins can transfer a stopped server from Servers. Select the destination Spark
and its host addresses and ports. Both Sparks need to be connected and the
destination needs sufficient resources and working filesystem quotas. Game
files and completed backups move; server identity, ownership, members, and
schedules stay attached. The destination remains stopped until started manually.
Transfers require temporary disk space on both hosts. Archives support up to
100 GiB of contents and 100,000 entries; links and special files are rejected.
Data travels over the existing authenticated Spark connections, without panel
disk staging or another public Spark port.

Transfer progress is durable and uploads resume after interruptions. Failed
transfers retain resource reservations; retry them from the transfer dialog.
The source is retained until the destination has verified the archive and
Campfire has committed the placement change. Cancellation is available before
that change; cancellation after copying starts needs both Sparks reachable.
Once placement changes, retry any cleanup failure to finish the transfer.
Server changes and operations are blocked while a transfer is active.

After moving or deleting all servers, remove the empty Spark from Sparks.
Removal rejects Sparks with servers or active transfers and revokes enrollment
credentials. Stop or uninstall the Spark service on its host afterward.

Linux binary installation
-------------------------
Release archives contain campfire, spark, this guide, configuration examples,
Compose configuration and systemd units. Select linux_amd64 for x86-64
or linux_arm64 for ARM64. Docker-built release binaries link SQLite and musl
statically. Native make build binaries use the local toolchain/libc instead.

Verify the downloaded archive's companion SHA-256 file from the same directory:

  sha256sum -c campfire_VERSION_linux_ARCH.tar.gz.sha256
  tar -xzf campfire_VERSION_linux_ARCH.tar.gz
  sudo install -m 0755 campfire /usr/local/bin/campfire
  sudo install -m 0755 spark /usr/local/bin/spark

Install only the binary needed on each host. Install the operating system's
CA certificates. Every execution host also needs rootful Docker Engine and
the Docker CLI. A host running only Campfire needs neither Docker nor Spark.

For a Campfire systemd installation:

  sudo useradd --system --home-dir /var/lib/campfire --shell /usr/sbin/nologin campfire
  sudo install -d -m 0750 /etc/campfire
  sudo install -m 0600 campfire.env.example /etc/campfire/campfire.env
  sudo install -m 0644 deploy/systemd/campfire.service /etc/systemd/system/

Edit /etc/campfire/campfire.env with your public URL and agent TLS settings,
then run:

  sudo systemctl daemon-reload
  sudo systemctl enable --now campfire.service
  sudo journalctl -u campfire.service -f

StateDirectory creates /var/lib/campfire with private permissions and the
service user's ownership. The panel listens on 127.0.0.1:8080 by default.
Do not run a development panel against this same database or port.

To host games on the same machine, also install and enroll Spark using the
instructions below. The Campfire unit needs no changes. Campfire and Spark use
separate state directories and can be updated or restarted independently.

First-run administrator setup
-----------------------------
Open the panel through your configured origin. Until the first account is
created, startup prints a one-time setup token to the console. For systemd:

  sudo journalctl -u campfire -b

For Docker:

  docker compose logs campfire

Enter that token in the setup form and create a password of at least 15
characters. The token becomes invalid after successful setup and is never
printed again once an account exists. It is kept only in memory as a hash;
restarting before setup completes generates a new token, so use the latest
startup output. No setup-token file is written. Browser sessions
expire after 12 hours absolutely or 30 minutes without API activity. Polling
counts as activity. Setup creates the initial Admin account; additional accounts
are created from Users or on first OIDC sign-in when configured. All management
APIs require an account with the relevant platform or server permissions; writes
also require CSRF protection.

Forgotten password recovery uses a private regular file, not a command-line
password. Create a mode-0600 file with your editor and run:

  sudo /usr/local/bin/campfire reset-password \
    --database /var/lib/campfire/panel.db --password-file /private/new-password

This preserves the username and revokes that administrator's sessions. Other
accounts remain signed in. Add --username NAME to recover a particular admin;
otherwise the first administrator is selected. Remove the password file after
recovery. Reset requires an administrator to have been configured. Admins reset
other users' passwords from Users.

Users, roles and server access
-----------------------------
Admins manage all users, roles, Sparks, Embers and servers. Users and Roles
are administrator-only pages. There is no public password account registration.

The built-in roles are Admin, Server creator and User. Server creators
can create servers only on Sparks approved for their role. On the
Sparks page, create or edit a Spark and use its Access step to grant creation
access. This grants no Spark
management rights. New roles can grant server creation or selected server-scoped
permissions; the built-in roles cannot be edited or deleted.

Creating a server makes its creator the Owner. Owners can operate, configure,
delete and share that server. Use the Access step before Review when creating
or editing a server and enter an existing username to assign an Operator.
Changes are applied when the wizard is saved. Several users can operate the
same server. Users with sharing permission but no configuration permission
can edit Access and Review without modifying the server configuration.
Operators have lifecycle, console, file and backup access but cannot change
configuration, delete the server or share access. Owners can assign operators;
only administrators can assign custom server roles or transfer ownership.

To create a server for another user, select its owner in the Access step as an
admin. Later ownership changes require confirmation when saving and remove the
previous owner's implicit access. Administrators
retain access to every server regardless of ownership or membership.

Server permissions are checked by the backend on every endpoint. Removing a
member or changing role permissions affects subsequent requests immediately.
Active backup downloads also recheck access between chunks. Disabling or changing
an account revokes that account's sessions. At least one enabled Admin must remain.
An account that owns servers must transfer them before it can be deleted. Roles
assigned to accounts or server members cannot be deleted. Removing a Spark's
provisioning grant does not remove users' ownership of existing servers.

Deleting an account is a soft delete: it disappears from account lists and cannot
sign in. Its sessions, API tokens and direct access grants are removed, schedules
running as that account are disabled, and its password hash is cleared. The user
record and OIDC identity remain for history and to prevent reprovisioning the
deleted identity. Deleted usernames remain reserved.

Current builds negotiate wire format 1 and individual
feature capabilities as described above.

Optional OpenID Connect login
----------------------------
Local username/password login remains enabled by default. To add OIDC, register
a web application with your identity provider and set these Campfire variables:

  CAMPFIRE_PUBLIC_URL=https://panel.example.com
  CAMPFIRE_OIDC_ISSUER=https://identity.example.com
  CAMPFIRE_OIDC_CLIENT_ID=campfire
  CAMPFIRE_OIDC_CLIENT_SECRET=your-provider-secret

Register this exact redirect URI at the provider:

  https://panel.example.com/api/v1/auth/oidc/callback

The provider must support the authorization code flow, PKCE S256 and the openid
and profile scopes. A client secret is optional for providers using public
clients. Protect the environment file containing it. HTTPS is required, with
loopback HTTP allowed for local development using an explicit public URL.
Compose forwards these settings from .env; systemd reads campfire.env. Matching
CLI flags are --oidc-issuer, --oidc-client-id and --oidc-client-secret.

Restart Campfire. The sign-in page now offers OpenID Connect alongside passwords.
Complete initial administrator setup locally before signing in with OIDC. New
provider identities create ordinary User accounts without server access. Their
usernames use the provider's preferred username plus a unique suffix; admins can
find them in Users and assign roles or servers. Email, names and provider groups
never select existing accounts or grant roles. Identity is the issuer + subject.

To use OIDC with an existing account, sign in to that account and choose Link
OpenID Connect in the sidebar. Complete provider authentication. The linked
identity signs into that same account and retains its roles and server access.
An identity already linked to another account cannot be reassigned this way.

To require OIDC for all logins:
1. Sign in as an administrator and link that account to the provider.
2. Sign out and verify that OpenID Connect signs in to the administrator account.
3. Set CAMPFIRE_DISABLE_LOCAL_LOGIN=true (or --disable-local-login) and restart.

Until an enabled administrator is linked to the configured issuer, Campfire
keeps initial setup and password login available even when this setting is true.
Without OIDC configured, password login also remains available. Once an enabled
administrator is linked, password login and setup endpoints are disabled; existing
password sessions are revoked. At least one OIDC-linked administrator
must remain enabled. Local accounts and passwords remain stored. To recover from
provider failure, set CAMPFIRE_DISABLE_LOCAL_LOGIN=false, restart, and use local
login or reset-password. Remove all OIDC settings to return to local-only login.

Provider tokens are verified and discarded; Campfire uses its own revocable
sessions afterward. Provider logout does not terminate Campfire sessions, and
Campfire sign-out does not sign out of the provider. Disable the Campfire user
to revoke access immediately. Provider outage prevents new OIDC sign-ins; it
does not invalidate existing Campfire sessions. Pending login/link flows expire
after five minutes and are cleared on restart. Identity bindings and session
provider tracking are included in the initial database schema.

Schedules and audit
-------------------
The Schedules page contains one-off and recurring definitions plus execution
history. Owners and admins can configure schedules; custom server roles need
server.configure and server.operate. Operators can view history and retry
supported failed operations on their assigned servers. Only admins can read Audit.

Choose Run once and a due date/time, or Recurring and a five-field cron expression
with a time zone. The one-off date input uses the browser's local time; the
database stores its UTC timestamp. Available actions are start, stop, restart,
kill, backup and console command. Backups require a stopped server; scheduling a
backup does not automatically stop a running game. Run now works for paused
schedules too. Commands remain private; leave a command blank while editing to
preserve its stored value.

Schedules run as the user who last saved them (run_as_user_id). Due definitions
stay pending while their Spark is disconnected or disabled. No run-history row is
created until an attempt starts. An atomic claim snapshots the current definition,
including its execution identity, and creates a dispatching run. A one-off schedule
then disables; a recurring schedule advances to its next due time. Missed recurring
occurrences coalesce into one attempt after downtime. The same schedule cannot
have overlapping attempts. Edits before a claim affect that attempt; edits, pauses
or deletion after the claim do not cancel its captured configuration. There are
no schedule version counters or pre-created queued runs.

Permissions and account state are checked again immediately before dispatch,
including after waiting for the server lock. Failed or skipped attempts stay in
history. Busy servers fail that attempt; uncertain node work is never replayed
automatically. The worker runs in the single active Campfire process; multiple
panel processes against one database remain unsupported.

Manual lifecycle operations and recurring work retain actor, server, action,
operation ID, state and timestamps. Node operation IDs match execution IDs.
Panel restarts mark in-flight operations interrupted; they are never silently
replayed. Check server state before using Retry, since uncertain work may already
have executed. Each retry creates a separate linked execution. Install, start,
stop, restart, kill and backup support retries. Reissue restore or console input
explicitly; command payloads are removed from terminal execution records.

Audit records administrative mutations, authentication attempts, denied mutations,
and final operation outcomes. Passwords, setup/enrollment tokens, OIDC codes,
console text, file contents and request/response bodies are not recorded.
Audit intent is persisted before a mutation; unavailable audit storage rejects
the request. Incomplete audit records are marked interrupted after restart.
History and audit survive account, schedule and server deletion; deleted-server
history remains visible to admins. Reads are paginated in batches of 100, with
exact action/target filters on Audit.
Audit records reference retained user profiles, including deleted accounts, so
administrators can still see their email and other public profile fields. The
username stored on each event is the historical username at the time of action.
Unauthenticated events and legacy records for already-removed users have no user
foreign key; their existing historical username is preserved.

Configure independent panel-wide history retention limits, for example:

  CAMPFIRE_AUDIT_RETENTION_DAYS=90
  CAMPFIRE_OPERATION_RETENTION_DAYS=30

Both default to 0, keeping records forever. Values must be whole days between
0 and 36500. The flags --audit-retention-days and --operation-retention-days
override the environment. For systemd, edit /etc/campfire/campfire.env and
restart campfire. With the supplied Compose file, set the variables in .env and
recreate the container with docker compose up -d. Policies apply to all users
and servers, including history retained after a server or account is deleted.

Audit ages use creation time. Operation history ages use completion time, so a
long-running operation gets its full retention period after it finishes. Only
terminal records are eligible: queued, dispatching and running operations and
pending audit requests are preserved. Schedule definitions and future runs are
unaffected. Expired records, including their retry data, are permanently removed.

Cleanup starts in the background at startup after recovery and normally runs
hourly. Each transaction removes at most 1000 records per collection; a backlog
continues in one-second intervals without holding one large write transaction.
Cleanup errors are logged and retried on the next hourly pass. History pages
use timestamp-and-ID cursors so pruning an already-viewed row does not break
pagination. The API before parameter accepts CREATED_AT:ID; a retained row ID
also works. Filters and access restrictions apply to every page.

SQLite reuses freed pages for future writes. Cleanup does not run VACUUM or
promise to shrink the database file immediately.
Schedules, executions and audit records are included in the initial database schema.
Schedules use the same negotiated Spark capabilities as manual operations.

HTTPS and agent enrollment
-------------------------
Set CAMPFIRE_PUBLIC_URL=https://panel.example.com for browser access through
an HTTPS reverse proxy. Proxy the entire origin to 127.0.0.1:8080; no separate
frontend server is needed. Non-loopback listeners require an explicit HTTPS
public URL.
For local development only, loopback HTTP is supported without a public URL.

Remote Sparks use a separate direct TLS listener, enabled by default on
0.0.0.0:8443. No manually provisioned certificate is required. Campfire creates
agent-https-authority.json and agent-https.json in its persistent state directory,
using private file permissions. Keep these files with the database and
spark-authority.json in backups. The HTTPS authority is separate from the
authority that authenticates Spark clients. Generated server certificates renew
before expiry without replacing the CA's signing key. Updated Sparks also
refresh the public CA certificate during authenticated client renewal, so
renewing the CA certificate does not leave their saved trust expired.

The public agent address defaults to the panel public URL's hostname and the
agent listener's port. For a different hostname or externally mapped port, set:

  CAMPFIRE_AGENT_PUBLIC_URL=https://agents.example.com:8443

That hostname/IP is included in the generated certificate. Loopback names and
addresses are also included. For local development without a panel public URL,
the public address defaults to localhost (or a specific listener address).
Changing the public hostname requires a panel restart to update the certificate.
Existing Sparks still need a valid saved address matching the certificate.
Set CAMPFIRE_AGENT_LISTEN to an empty value to disable the listener explicitly.
Mock mode disables it automatically.

Optional overrides:

  CAMPFIRE_AGENT_LISTEN=0.0.0.0:8443
  CAMPFIRE_AGENT_TLS_CERT=/etc/campfire/tls/panel.crt
  CAMPFIRE_AGENT_TLS_KEY=/etc/campfire/tls/panel.key

When overriding TLS, supply both certificate paths and use a server certificate
matching the hostname agents connect to. Certificate
files must be readable by the service user; protect the private key with
restricted owner/group permissions. Open port 8443 to the Spark hosts. An
ordinary TLS-terminating reverse proxy does not preserve the agent's mutual
TLS authentication. Keep the direct listener or use TLS passthrough.

After adding a Spark in the panel, the installation helper provides a copyable
command with the configured agent address and, for generated TLS, its public CA
certificate embedded. The CA is delivered through the authenticated browser
session and written to a temporary file by the installer before enrollment;
Spark saves it in its private identity. TLS and hostname verification remain
enabled; the installer never uses --insecure. Set the dedicated agent HTTPS
address (not the browser address unless both listeners are explicitly routed
that way), then run it on the game host.
The same helper is available through Re-enroll in the Spark details drawer,
with a confirmation explaining that successful re-enrollment replaces the
existing credentials and briefly restarts the Spark service.

The helper requires Linux amd64/arm64, a running Docker daemon, systemd, curl,
and sudo access. It lists all missing command dependencies before installing
anything. It downloads the latest stable tagged GitHub release, verifies
the archive's SHA-256 checksum, saves the agent identity in /var/lib/spark,
installs /usr/local/bin/spark and spark.service, and enables the service.
The release must support --enroll-only. For a custom private HTTPS certificate,
provide the path to its CA file on the game host; generated TLS needs no manual
CA file. The helper also requires the base64 utility. The command includes a
single-use token that expires after fifteen minutes; generate another if needed.
The token is removed after installation and is not kept in the service config.
Existing Spark installations retain their data; an active service is stopped
while enrollment is updated and restarted afterward. The installer installs a
systemd drop-in that uses /var/lib/spark and the saved identity, bypassing an
older /etc/campfire/spark.env enrollment configuration.

For manual installation, on a game host install spark and Docker, then:

  sudo install -d -m 0750 /etc/campfire
  sudo install -m 0600 spark.env.example /etc/campfire/spark.env
  sudo install -m 0644 deploy/systemd/spark.service /etc/systemd/system/

Create a Spark in the panel and generate its short-lived enrollment
token. Save it on the node in /etc/campfire/enrollment.token (mode 0600).
Set SPARK_PANEL=https://panel.example.com:8443 and
SPARK_TOKEN_FILE=/etc/campfire/enrollment.token in spark.env. For a private
certificate authority, also set SPARK_CA_FILE to its certificate file.

For a same-host Spark, use the panel's agent hostname or
https://127.0.0.1:8443 if the certificate includes 127.0.0.1 in its IP subject
alternative names. This is the agent connection address. The Spark's game
address in the panel is separate: use an address players can reach, such as
the host's LAN IP or public address, rather than loopback.

  sudo systemctl daemon-reload
  sudo systemctl enable --now spark.service
  sudo journalctl -u spark.service -f

After successful enrollment, remove SPARK_TOKEN_FILE from spark.env and remove
the one-time token file. Subsequent starts use /var/lib/spark/identity.json.
The root-run service manages Docker and game ownership. Its state must live
on the same execution host as the Docker daemon, at visible absolute paths.

Docker / Compose installation
-----------------------------
The image runs as UID/GID 10001, contains no Docker CLI, and
does not mount the host Docker socket. Game servers run on binary Sparks.
Use the release archive's compose.yaml and .env.example, or equivalent settings.

Copy .env.example to .env and set CAMPFIRE_IMAGE to the version published by
GitHub CI and CAMPFIRE_PUBLIC_URL to your HTTPS browser origin. The agent TLS
certificate and CA are generated and persisted automatically. Optionally set
CAMPFIRE_AGENT_PUBLIC_URL for a different agent hostname or external port.

  docker compose config --quiet
  docker compose pull
  docker compose up -d
  docker compose logs -f campfire

Compose publishes browser HTTP only on 127.0.0.1:8080 for a host HTTPS proxy.
It publishes agent TLS on port 8443 and persists the database, generated TLS
credentials and private signing authorities in the campfire-data named volume.
Its root filesystem is read-only with a bounded temporary directory, dropped
capabilities and no-new-privileges. Named volumes initialize with the image's
10001 ownership. Pre-existing bind-mounted state needs that ownership explicitly.

To use your own certificate, add compose.agent-tls.yaml to the Compose command
(-f compose.yaml -f compose.agent-tls.yaml) and set CAMPFIRE_TLS_DIR to an existing
directory containing panel.crt and panel.key. This is also required when moving
an existing Compose deployment with custom certificates to the new base Compose
file: keep using the same custom certificate so enrolled Sparks retain trust.
Do not switch an enrolled fleet's CA without explicitly distributing the new
trust or re-enrolling it. For Linux, a private example layout is root:10001
ownership, directory mode 0750, certificate mode 0644 and key mode 0640. The
container must be able to traverse the directory and read both files. The
override mounts this directory read-only.

Image tags use ghcr.io/OWNER/REPOSITORY:VERSION. Compose deploys the CI-built
image and does not build from local source. No image has been published just
by adding these files. Authenticate to GHCR on deployment hosts if the
published package is private.

For password recovery, create the private file in the container's writable data
volume (for example docker compose cp a local mode-0600 file and then set its
ownership to 10001 using a root exec). Then:

  docker compose exec campfire campfire reset-password \
    --password-file /var/lib/campfire/new-password

Remove both temporary password files after recovery. The image's default
CAMPFIRE_DATABASE selects the correct persistent database for this command.

Backup, upgrade and rollback
----------------------------
Keep the panel database together with spark-authority.json. Keep each Spark's
identity.json, delivered definitions, runtime metadata, game data and backups.
Game backups are not a substitute for panel database/identity backups.

Before upgrading, stop the panel service/container and take a consistent copy
of its entire state directory or named volume. Copying just a live SQLite file
can omit WAL contents. Store state backups privately. Record the current
binary/image version and the database schema version.

With PostgreSQL, also take a consistent database backup using pg_dump or your
database provider's backup tooling while Campfire is stopped. The panel state
directory still contains private identities and must be backed up alongside it.

For binary upgrades, stop the relevant service, preserve its old binary,
verify and install the new one, then start the service and check the journal,
health endpoint, login and node connections. Use a stopped Spark and preserve
its state when upgrading its binary. Detached games continue across ordinary
agent disconnects; wait for lifecycle/file/backup work to finish before stopping
an agent. Breaking wire protocol changes require compatible panel and Spark
versions. The panel uses schema 1 and currently supports wire format 1. Update
either component independently while their wire-version ranges overlap and
their shared capabilities cover the features you use. A missing optional
capability blocks that feature; a disjoint wire range blocks the connection.

For Docker upgrades, stop campfire, back up campfire-data, set CAMPFIRE_IMAGE to
the new CI-published version, then docker compose pull and docker compose up -d
and verify its health and nodes.
Never use docker compose down -v for an upgrade: it removes persistent state.

Database migrations run automatically at startup. A previous binary may reject
an upgraded database. Roll back the binary/image AND restore the matching
pre-upgrade panel state backup while the panel is stopped. Do not drop tables
or delete private signing keys to bypass a schema/version error.

Local development with simulated Sparks
--------------------------------------
After make dependencies, run from the repository root:

  make dev-mock

Alternatively run pnpm --dir web run dev:mock. Open http://127.0.0.1:8081
and sign in with admin / campfire-dev-password. This is a real local panel:
authentication, permissions, database writes, schedules, notifications and audit
records use their normal code paths. Only the Spark transport is simulated.
The UI displays a Mock mode label. No Docker, DNS, TLS or production secrets
are required. The mock executable ignores CAMPFIRE_* environment settings and
always uses a loopback listener with its own data/mock/panel.db database.

Each fresh runner session seeds three Sparks (two online and one offline), five
game servers, mock Ember revisions, a recurring restart schedule and inbox messages.
Lifecycle actions complete immediately, metrics vary over time, console input
appears in the output stream, and the text file editor supports small files
with revision checks.
Mock installed servers report verified disk quotas; simulated game-data usage
includes editable files, and writes exceeding the allocation are rejected.
State survives watcher-triggered backend rebuilds and frontend reloads within
the same runner session. Stopping and starting make dev-mock or dev:mock clears
only data/mock and starts fresh. Running the mock binary directly preserves state.
Europe starts on an outdated simulated Spark client; its Update Spark action
updates the persisted mock version without contacting GitHub or replacing a binary.
Ember update ready is stopped on an old applied revision, with the current local
mock-minecraft definition ready to apply through Update Ember.

Server transfers, archive operations, binary uploads, real installers
and Docker execution are not simulated. Unsupported operations report an error
rather than claiming success; test these against real Sparks after deployment.
The dedicated campfire-mock executable and simulator are excluded by the
production build tag. Production Campfire has no mock-mode flag.

The runner rebuilds Go changes and hot-reloads the frontend. Mock builds disable
Go compiler optimizations so a debugger can inspect variables. For a debugger
that launches its own backend, stop the runner, then use two terminals from the
repository root (with Delve installed):

  go -C backend build -gcflags='all=-N -l' -o ../bin/campfire-mock ./cmd/campfire-mock
  dlv exec ./bin/campfire-mock

  VITE_CAMPFIRE_MOCK=true make dev-ui

The mock executable uses data/mock relative to its working directory; launch
it from the repository root to reuse the runner's fixtures and edits.

Building releases from source
-----------------------------
Native builds require Go 1.26+, a C compiler for SQLite, Node 24+ and the pinned
pnpm version. Run make dependencies, then make check. To run the repository suite
against PostgreSQL as well, set CAMPFIRE_TEST_POSTGRES to a disposable database
URL and run make test-postgres. Tests create and drop isolated schemas; the test
account needs CREATE SCHEMA access. CI runs both backends.
make build compiles the frontend, stages generated assets into
backend/internal/campfire/webui/dist, and
builds bin/campfire with the production tag. Direct go build uses development
mode and serves APIs without bundled frontend assets; use make dev with Vite.
make build-campfire builds only the panel and bundled UI. make build-spark builds
only the agent and does not need Node or frontend assets. The panel dependency
graph excludes the game runtime; the Spark agent initializes its own runtime.

  make build VERSION=v0.1.0 COMMIT=COMMIT_SHA BUILD_DATE=RFC3339_TIMESTAMP
  ./bin/campfire --version
  ./bin/spark --version

GitHub CI validates pushes to master, version tags and pull requests into master.
Only successful push builds publish packages, following the DockDash strategy:

  master push: ghcr.io/dougmaitelli/campfire:dev
  v1.2.3 tag: :v1.2.3, :v1.2, :v1 and :latest

Images support Linux amd64 and arm64, built on native runners. Architecture
images are merged by digest after both builds succeed. Pull requests and manual
CI runs validate without publishing images or GitHub Releases.

Only version-tag pushes create GitHub Releases. Each release attaches portable
Linux amd64/arm64 archives containing the Campfire and Spark binaries,
installation files and SHA-256 checksums. Binaries are statically linked with
musl for hosts without a matching glibc. Release notes are generated by GitHub.
Generated output is ignored by Git.

Release tags use vMAJOR.MINOR.PATCH, optionally followed by a SemVer prerelease
suffix, such as v1.2.3-rc.1. Prereleases publish their full image tag and a GitHub
prerelease; they do not move :latest or the major/minor aliases. Build metadata
suffixes (+...) are not accepted as Docker/package versions. All release and
image publication depends on the full CI validation succeeding.

Monitoring
----------
The Dashboard and server list show measured CPU, memory and game-data usage.
CPU is expressed in cores (100% Docker CPU equals one core). Memory excludes
reclaimable filesystem cache, matching Docker's memory usage calculation.
Disk usage counts logical sizes of regular files in the server data directory;
hard links count once, and symlinks, backups and Docker image layers are excluded.
These logical sizes can differ from the filesystem blocks charged to a quota.

Spark enforces each server's game-data allocation with Linux project quotas.
Execution hosts require Linux 5.14 or newer, root privileges, and XFS or ext4
with project quota accounting AND enforcement enabled on the filesystem holding
SPARK_DATA/runtime. XFS needs the prjquota (or pquota) mount option; ext4 also
needs its project and quota filesystem features and project quotas enabled.
Prepare the filesystem using its distribution's filesystem administration tools
before starting Spark. Spark does not format filesystems or change mount options.
Install, start and file writes fail if a matching quota cannot be established;
there is no fallback to periodic size checks. Status and monitoring report
whether the current allocation was verified as enforced.

Use one Spark data directory per execution filesystem. Reserve project IDs
1073741824 through 2147483647 for Campfire on that filesystem. Spark records
ownership in runtime/.quota-projects; retain this directory with the runtime
data. IDs and quota records are deliberately not recycled after deletion,
because deleted files may still have open descriptors and charged blocks.
Unmanaged nonempty game-data directories are rejected instead of silently
adopted. Moving runtime data to another filesystem requires fresh quota setup.

The hard limit covers game-data filesystem blocks, including directory space,
preallocation and open deleted files. Writes can fail before logical file sizes
reach the allocation. Freeing data or increasing the allocation permits writes
again. Disk allocation changes are applied before the next install, start or
file write; shrinking below charged usage is rejected. File deletion remains
available when a quota is full or requires repair. Temporary files for atomic
saves need quota headroom. Quotas remain active without a Spark connection.

Restores stage a separately quota-limited directory before replacing the original;
both copies temporarily consume host space. Backups, images, container writable
layers and bounded Docker logs are outside the game-data allocation and still
require host free-space management. Docker's --storage-opt size limits its
writable layer and does not constrain our bind-mounted game directories.
Installer and game containers use Docker's default seccomp policy with additional
restrictions on filesystem attribute writes that could change quota assignments.
Docker must support seccomp. The upstream profile and its license are included
under backend/internal/spark/runtime/seccomp.

Spark caches container measurements for one second and disk measurements for
30 seconds. The dashboard polls one second after each response, without
overlapping requests, and marks old readings stale.
Unavailable readings stay unavailable rather than becoming zero. The first CPU
sample may need another polling interval to establish a baseline. Measurements
are live snapshots, without persistent metric history. Background monitoring
evaluates these snapshots for health and resource alerts (see Notifications).

Users see only servers they can view. Administrators also see Spark connection
status and configured capacity; these capacity figures are not host OS usage.
Upgrade Spark alongside Campfire to enable measurements. Docker statistics
require Spark's local Unix Docker socket; remote Docker contexts are unsupported.

Console streaming
-----------------
The console streams Docker stdout and stderr continuously over the authenticated
Spark connection, then to the browser using server-sent events. Input commands
continue to use authenticated, CSRF-protected requests. Opening a console does
not deploy configuration or prevent lifecycle operations.

Each connection starts with Docker's latest 200 lines and then follows new output.
The browser retains the latest 256K characters. Automatic reconnection replaces displayed
history instead of appending duplicates; this is not durable log storage or a
guarantee of replay across disconnected periods. Installer output is streamed
while installing, with saved installer output available after completion.

Each Spark connection permits 16 simultaneous console viewers. Stream buffers
are bounded and apply backpressure; interrupted viewers reconnect rather than
silently losing output. Closing
the console cancels its Docker reader. Active streams recheck session, server
permission and Spark eligibility at least every five seconds.

Console streaming requires server.console.stream.v1. Unsupported Sparks can
stay connected for other negotiated operations. No database migration or
re-enrollment is required for capability negotiation. HTTP proxies
must forward streaming responses without buffering; the endpoint sends regular
heartbeats and X-Accel-Buffering: no.

Egg compatibility
-----------------
Embers can be imported from native definitions or Pterodactyl/Pelican Egg exports
in JSON or YAML. The import drawer previews conversion, lists unsupported fields
and requires acknowledgement of compatibility warnings. An import saves only a
new Ember; it does not run the supplied installer or pull any images.
URL imports retain their source as the native Ember updateUrl. A definition's
own updateUrl, or an Egg's meta.update_url, takes precedence over the import URL.
This metadata is kept through preview, conversion and saving. Campfire checks
each imported revision's update URL on startup when due and about every 24 hours
afterward. A background worker looks for due checks every ten minutes. Check
times, failures and availability are stored on each Ember row.
The Embers page provides a shared Check updates action and per-Ember Update
update actions. Last-check timestamps are kept internally for daily scheduling.
Downloads open the import review flow and require the usual warning review before
replacing the local definition. Existing servers keep their applied revision
until an administrator applies the update explicitly. Formatting and JSON object-key order do not count as
new versions; changes to the parsed game definition do. Checks use the same public
HTTPS restrictions and size limits as URL imports. No URL means no automatic check.
Mock development mode seeds both an available update and an up-to-date Ember.
Check updates and Download update use fixed local mock responses without network
requests; accepting a mock update replaces its local definition and survives reloads.

See deploy/EGG-COMPATIBILITY.txt for the format and feature support matrix,
fixture coverage, API request examples and runtime limitations. Native definitions
and converted Eggs both use Ember schema 1. Egg conversion does not change the
database schema. Extended config parsers, readiness and stop templates require
the negotiated server.ember.behavior.v1 Spark capability.
